# Narrative Architecture System (NAS)

**Working draft — v0.2 (April 2026)**
*Methodology for structured fiction development. This document is the spec for the writing layer of the surrounding software; project-level features (kanban, panels, dashboards, session UX) wrap NAS but are out of scope here.*

Replaces `NAS_Narrative_Architecture_System.docx` v1.0, which was a rough mush of multiple source files.

---

## 0. Scope and Stance

**What NAS is:** a methodology that turns story development into a system of explicit objects, states, and operations — so a writer can manage a complex narrative the way an engineer manages a complex codebase.

**What NAS is not:** a project-management system. NAS does not concern itself with chapter-level kanban, daily writing sessions, productivity dashboards, deadlines, or visual layouts. Those are features of the software that wraps NAS, not part of the writing system itself.

**Design stance:** every concept in NAS must compile to a data model — properties, operations, invariants. If a concept can only be expressed in metaphor, it isn't pulling its weight, and it doesn't belong here.

**Why the system is shaped this way:** phase separation, externalised state, and explicit transitions are themselves the executive-function support that makes large narrative work tractable for technical/neurodivergent minds. This is the *motivation* of the framework, not a separate pillar.

---

## 1. Core Data Model

NAS is built around ten primitive object types. Everything else (workflows, views, phases) is operations on these objects.

| Object | One-line role |
|---|---|
| **Character** | An agent with state, behaviour, and an arc |
| **Relationship** | A directed edge between two characters with state |
| **Scene** | The atomic unit of authored prose |
| **Setup** | A planted element awaiting payoff |
| **Payoff** | A consumption/closure of one or more setups |
| **ReaderKnowledge** | What the reader knows / suspects / wants / fears at a point in the timeline |
| **BibleEntry** | A canonical world fact (rule, location, faction, history) |
| **Theme** | A thread woven through scenes |
| **Stake** | Something at risk for a character / faction / world |
| **Retcon** | A documented edit to a previously canon fact, with impact closure |

Each is detailed below. The remaining sections describe operations and views over these objects.

## 2. Character

A character is a typed object with **properties**, **methods**, **invariants**, and an **arc**.

### 2.1 Properties

```yaml
identity:
  name: string
  age: int | range
  species: string
  background: string
psychological:
  core_wound: string         # the original injury
  dominant_fear: string
  desire: string
  internal_contradiction: string
relational:
  attachment_style: enum     # secure / anxious / avoidant / disorganized
  default_power_position: enum   # dominant / equal / submissive
functional:
  skills: [string]
  narrative_role: enum       # protagonist / antagonist / foil / mentor / etc.
  voice_patterns: [string]   # speech tics, vocabulary, sentence rhythm
```

### 2.2 Methods

Methods are **decision heuristics** — how the character acts under specific stimuli. This is the leverage of OOP-as-applied-to-character: when a scene drafts a character making a choice, the writer can check the choice against the methods.

```yaml
methods:
  under_fear: "withdraws, plans escape, lies to buy time"
  under_betrayal: "cuts contact silently; never confronts"
  under_love: "tests the other person before letting them in"
  under_authority: "outwardly compliant, inwardly contemptuous"
```

Methods can be overridden by sub-classed characters (e.g., a Sithernis-lineage character may override `under_betrayal` to "confronts publicly").

### 2.3 Invariants

Invariants are assertions that should always hold. Violating an invariant flags a consistency check — not necessarily a bug, but a signal that either the scene is wrong or the violation is intentional and must be marked as such.

```yaml
invariants:
  - "Never lies to her sister, even when costly"
  - "Refuses to use Sithernis magic before chapter 12 (canonised vow)"
```

A scene that breaks an invariant must declare `intentional_break: reason`.

### 2.4 Arc

```yaml
arc:
  start_state: string
  transformation_vector: string    # what is changing, in what direction
  end_state: string
  milestones:
    - chapter: int
      state: string
```

### 2.5 Inheritance and Composition

A character may **inherit** from a lineage (family, order, archetype). Inheritance brings default methods, invariants, and properties; the child can override.

```yaml
inherits: [SithernisLineage]
overrides:
  invariants:
    - "Refuses lineage's blood-oath tradition"
```

**Composition** adds traits — bundles of properties/methods that don't form a class hierarchy (e.g., `TraumatizedByWar`, `TrainedHealer`). Composition expresses *lived experience*; inheritance expresses *origin*.

## 3. Relationship

A relationship is a **directed edge** between two characters. Directed because A's view of B is not always B's view of A.

```yaml
from: CharacterID
to: CharacterID
properties:
  trust: float [-1, 1]
  power_differential: float [-1, 1]   # negative if 'from' has less power
  emotional_valence: enum             # love / loyalty / rivalry / contempt / fear / etc.
  history: [event_id]
state_log:
  - chapter: int
    delta: { trust: -0.3, valence: "rivalry → contempt" }
    cause: scene_id
```

The state evolves through tracked **mutations**. A scene that changes a relationship records the delta in its scene metadata and the relationship's `state_log`. Vague drift ("they grow distant over time") is unacceptable; the change must point to the scene that caused it.

## 4. Scene

The scene is the atomic build unit of NAS. Everything that gets written lives inside a scene.

### 4.1 Anatomy

```yaml
id: "ch04.s02"
narrative_function: string                       # what this scene does for the story
characters_present: [character_id]
pov: character_id | "omniscient"
entry_state:
  - character: id
    emotional: string
    situational: string
exit_state:
  - character: id
    delta: string
information_delivered_to_reader: [reader_op]     # see §6
setups_planted: [setup_id]
payoffs_resolved: [payoff_id]
themes_touched: [theme_id]
stakes_active: [stake_id]
relationship_deltas: [{ edge: id, delta: ... }]
phase: enum                                       # rough | detailed | shaded | inked
```

### 4.2 The Phase State Machine

The four phases are formal states with explicit entry/exit criteria. **No phase may be entered until the previous phase's exit criteria are satisfied.** This is what prevents premature polish (the most common writing failure mode).

| Phase | Goal | Exit criteria |
|---|---|---|
| **Rough** | Establish narrative function, entry/exit state, info delivered | All four scene-anatomy fields filled; no prose yet |
| **Detailed** | Cause-and-effect sequence, functional dialogue, emotional beats | Scene readable end-to-end as continuous (rough) prose; setups/payoffs identified; relationship deltas logged |
| **Shaded** | Sensory texture, subtext, interiority, thematic resonance | Consistency check (§4.3) passes; theme tags justified by content |
| **Inked** | Final prose: language, rhythm, word choice | Read-aloud pass complete; no placeholder text remaining |

A scene may **regress** (e.g., Inked → Shaded) when a retcon invalidates it. Regression is tracked, not silent.

### 4.3 Consistency Check

Before a scene can leave Shaded, it must pass:

1. **Character state check** — each character's entry state matches their exit state from the previous scene they appeared in (or has an `intentional_break` reason).
2. **Bible check** — no claim in the scene contradicts a BibleEntry, unless the scene *is* the canonising event.
3. **Setup/payoff check** — every setup planted has at least a planned payoff window; every payoff resolved references valid setup(s).
4. **Invariant check** — no character action violates an invariant without `intentional_break: reason`.

The software surfaces check failures; the writer resolves them.

### 4.4 One File Per Scene

Each scene is a single markdown file with frontmatter (the anatomy above) and four sections, one per phase. The previous v1.0 scheme of four files per scene (`rough_sketch.md`, `detailed_sketch.md`, `shaded_version.md`, `final_draft.md`) is dropped: it scattered the scene across the filesystem and obscured progression. One file, one scene, with a `phase:` field tracking current state.

## 5. Setup / Payoff

Setup and payoff are **first-class objects**, not implicit prose patterns. Treating them as objects is what turns Chekhov's gun from a guideline into a tractable problem.

### 5.1 Setup

```yaml
id: setup_036
planted_in: scene_id
content: "Lysandra hides a locket in chapter 3"
type: enum                  # promise | question | foreshadowing | object | knowledge_gap
weight: enum                # major | minor
expected_payoff_window:
  earliest: ch_id
  latest: ch_id
status: enum                # open | resolved | abandoned (deliberate) | orphaned (accidental)
```

### 5.2 Payoff

```yaml
id: payoff_017
resolves: [setup_036, setup_041]
resolved_in: scene_id
mode: enum                  # direct | subverted | recontextualized
```

An **abandoned** setup is a deliberate choice (not every promise pays off — sometimes that's the point). An **orphaned** setup is a bug: planted and forgotten. The system distinguishes the two by writer intent, surfaced explicitly.

### 5.3 Queries

The setup/payoff graph is queryable:

- **Open setups at chapter N** — what promises are unresolved at this point?
- **Long-haul setups** — open for >K chapters; may need a reminder beat.
- **Orphans** — flagged for review.
- **Payoffs without setups** — usually a sign that a setup got edited away.

## 6. Reader Knowledge

The reader is a tracked entity. **What the reader knows at any point in the story is itself a state, mutated by scenes.** This is the layer that makes setup/payoff, dramatic irony, and reveals tractable. Without it, those concepts live only in the writer's head and drift silently.

```yaml
reader_state_at: scene_id           # state AFTER this scene
knows:
  - fact_id: "Lysandra is Sithernis-born"
    confidence: enum                # confirmed | strongly_implied | hinted | suspected
    learned_in: scene_id
suspects:
  - claim: "Raffaele is the betrayer"
    intensity: float [0, 1]
    planted_in: [scene_id]
wants:
  - "Lysandra to confront her mother"
fears:
  - "Raffaele will discover the locket"
```

### 6.1 Reader Operations

A scene can perform these operations on reader state:

- **Reveal** — confirm a fact (`suspected` → `confirmed`).
- **Foreshadow** — introduce a hint (`∅` → `hinted`).
- **Mislead** — deliberately raise confidence in a wrong belief.
- **Subvert** — replace a confirmed belief with its opposite (rare, costly).
- **Reframe** — keep the fact, change its meaning.

### 6.2 Dramatic Irony

Dramatic irony is the **gap** between a character's knowledge and the reader's. NAS makes this gap explicit: at any scene, the writer can ask "what does the reader know that this character doesn't?" and use the gap deliberately.

## 7. Story Bible

The Bible is the canonical source of truth — the read-only reference all scenes must respect.

### 7.1 Sections

- **World rules** — magic system, physical laws, technology level
- **Timeline canon** — historical events, dates, eras
- **Character registry** — full character objects (§2)
- **Relationship graph** — current state of all edges (§3)
- **Locations and factions** — geopolitical structure
- **Themes** — registered themes with current expression status (§9)
- **Open questions** — unresolved decisions, with priority
- **Retcon log** — every edit to canon (§8)

### 7.2 BibleEntry

```yaml
id: bible_world_magic_001
section: enum
title: string
content: prose
status: enum                  # canon | provisional | open_question
canonised_in: scene_id | "pre-narrative"
depends_on: [bible_id]        # other bible facts this one builds on
referenced_by: [scene_id]     # populated by the system, not authored
```

The `referenced_by` field is the cache that makes retcons tractable (§8).

### 7.3 Open Questions

Open questions are first-class. The software surfaces them; the writer resolves them as the story demands.

```yaml
id: q_017
question: "What does Sithernis blood-magic cost the user physically?"
blocking: [scene_id]          # scenes that need this answered before they can leave Detailed
priority: enum
proposed_answers: [string]
```

A scene that depends on an open question cannot leave Detailed phase until the question is resolved — the software enforces this.

## 8. Retcon and Cache Invalidation

A **retcon** is an edit to a BibleEntry, a canonised scene event, or a character invariant. NAS treats retcons as serious operations with a tracked impact closure — the equivalent of a dirty-cache rebuild.

```yaml
id: retcon_004
target: bible_id | scene_event_id | character_invariant_id
date: iso8601
old: string
new: string
rationale: string
impact_closure:
  scenes: [scene_id]          # scenes that referenced the old fact
  setups: [setup_id]
  payoffs: [payoff_id]
  bible_entries: [bible_id]
status: enum                  # proposed | accepted | propagated
```

**Workflow:**

1. Writer proposes a retcon, edits the target.
2. System computes `impact_closure` by walking the `referenced_by` graph.
3. Every node in the closure is marked **stale**.
4. Stale scenes regress to Shaded (or earlier if the change is structural).
5. Writer visits each stale node and either confirms "still valid" (mark clean) or rewrites.
6. When closure is empty, retcon status → `propagated`.

Without this mechanism, retcons silently corrupt downstream scenes. With it, the writer always knows what's been touched by what.

## 9. Theme and Stake

### 9.1 Theme

```yaml
id: theme_inheritance
name: "the cost of inherited identity"
expression_status: enum       # introduced | developed | challenged | resolved
expressed_in: [scene_id]
```

Each scene tags which theme(s) it serves. A theme that has no scenes after chapter N is effectively dropped — the system flags this as drift.

### 9.2 Stake

A stake is something **at risk** for a character, relationship, faction, or world. Stakes give the reader something to want and fear.

```yaml
id: stake_07
holder: character_id | faction_id | "world"
what_is_at_risk: string
introduced_in: scene_id
escalation_log:
  - scene: id
    new_state: string
resolved_in: scene_id | null
```

A scene that doesn't touch any active stake is suspect — possibly filler, possibly correctly a breath-beat. The system flags; the writer judges.

## 10. Branching

Branches are first-class versions of the manuscript that diverge from `main` and may merge back.

| Branch type | Purpose | Merge expectation |
|---|---|---|
| `main` | Canon narrative | Stable; tagged at chapter completion |
| `draft/[chapter]` | Active work on a single chapter | Merges to main when the chapter passes Inked + consistency |
| `whatif/[scenario]` | Alternative timeline experiment | May or may not merge; often kept as exploration |
| `character/[name]` | Deep arc / backstory exploration | Merges piecemeal — relevant material gets cherry-picked into bible or scenes |
| `timeline/[era]` | Historical period expansion | Merges into bible (timeline canon), rarely into manuscript |

**Definition of "stable on `main`":** every chapter on main has all scenes at Inked, consistency check passes, no orphan setups, no stale nodes from un-propagated retcons.

**Definition of a "release":** a chapter merged into main with a tagged version (`v1.0-ch04`).

**Merge protocol:** the writer reviews diffs scene-by-scene; the software runs the consistency check on the merged state before allowing the merge.

---

## 11. Versioning Conventions

The legacy file-naming convention (`OLD_`, `v1_`, `Claude_v[n]_`) is preserved only for **archived material** in `/Archive`. Active work uses git branches (§10); files in working folders are not version-prefixed.

**Rule of thumb:** prefix-versioning is for *snapshots that might be referenced as alternates*; git is for *the live working state*. Two systems, sharply distinct, no overlap.

## 12. The Authoring Surface

Each object type lives in a markdown file with YAML frontmatter. This keeps NAS files portable, diffable, and editable without the software — the software is a structured layer over portable text, never a lock-in.

```
/[ProjectName]
  /Characters/
    lysandra.md                 # frontmatter = character object
    raffaele.md
  /Relationships/
    lysandra__raffaele.md
  /Bible/
    world/magic.md
    world/timeline.md
    factions/
    locations/
    open_questions.md
    retcon_log.md
  /Themes/
    inheritance.md
  /Setups/                      # one file per setup, or grouped if small
    ch03_locket.md
  /Scenes/
    ch01/s01.md                 # frontmatter + four sections (rough/detailed/shaded/inked)
    ch01/s02.md
  /Branches/                    # populated by git, normally empty in main
  /Archive/
    OLD_*
    v1_*
```

## 13. What's Out of Scope

These belong to the software, not NAS:

- Kanban / chapter status board
- Per-day writing session UI
- Project dashboards, word-count tracking, deadlines
- Visual relationship-graph rendering
- Character portrait management
- Export to publishable formats
- Daily session templates and productivity routines

The software consumes NAS objects to produce these surfaces. None of them are part of the writing methodology itself.

## 14. Open Design Questions

Tracked here so they don't get lost. Each gets resolved or moved into the spec proper before NAS is locked.

- **Multi-POV scenes:** does a scene have one POV or can it have several? If several, how is reader-state mutation attributed?
- **Subscene granularity:** are beats inside a scene addressable, or is the scene the smallest unit?
- **Voice as object vs property:** is character voice a string list, or its own object with rules ("never uses contractions," "metaphors drawn from sailing")?
- **Worldbuilding without prose:** can a BibleEntry be canonised without ever appearing in a scene? Probably yes — but flag for cost/value review.
- **Reader-state on reread:** a rereader's knowledge differs from a first reader's. Do we model first-read vs reread separately, or only the first-read trajectory?
- **Theme weight per chapter:** should themes have a quantitative presence-per-chapter so we can detect drift?
- **Granularity of retcon impact:** does a retcon to a minor bible fact need full closure walking, or is there a "trivial retcon" path?
